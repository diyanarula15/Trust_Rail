## Post-Epic 10: live checking, plain language, and a real landing page
- **Status:** complete; verified against the live stack on macOS. Requested directly: show the check happening in real time, in language the general public understands, with a better landing page explaining each feature.
- **Why:** the evidence panel from the previous entry convinced a technologist and nobody else. "10 of 64 bits differ" is meaningless to an investor, the result appeared as one atomic blob after a spinner, and the landing page was three link cards with no explanation of what any of it did.
- **What shipped:**
  - **Live checking, genuinely streamed.** New `POST /api/verify/stream` emits Server-Sent Events as each pipeline stage actually completes. The existing `POST /api/verify` contract is untouched: both endpoints drain the *same* generator `_run_verification()`, so a streamed run and a plain run cannot drift apart. Stage order now follows `decide()`'s logical order (signature → registry → claims/risk) rather than the incidental computation order; claims and risk are independent of the registry sweep, so moving them after it changes nothing and reads correctly live.
  - **Plain-language register.** New `plain` block in both locales: all five verdicts and all 28 reason codes rewritten for a reader who has never heard of a hash, plus a `live` block naming each stage ("Comparing it with everything issuers have published"). The card now leads with `plain_headline`/`plain_body`; the formal §11 copy and the raw reason codes move behind a "Formal result codes" disclosure. Both registers come from i18n, so §12.1 still holds: the frontend invents no wording.
  - **The evidence panel, reframed.** Leads with two facts and the sentence that reconciles them: **"The file was changed" / "What it shows is unchanged"**, then an explanation of why forwarding rewrites a file without changing the picture. The hashes, the 8x8 bit grids and the distance scale are all still there, one click away under "Show the technical detail."
  - **Landing page rewritten** around what someone actually needs: a hero that states the question it answers, how it works in three steps, a call-out explaining why forwarding doesn't break matching, all five possible answers with what each means, and a card per feature (verify / issuer / public record / registry / supervision) explaining what it is *for* rather than just linking to it. Closes with an honest "what this is" note: fictional data, real cryptography.
  - `components/LiveCheck.tsx`, `lib/useLiveVerification.ts`, and a `verifyStream()` client built on fetch + ReadableStream (EventSource can't POST a file).
- **The honesty question this raised, and how it was answered:** "show it in real time" invites faking latency. The image pipeline finishes in ~40ms end to end, which would flash past unreadably. **Nothing here fabricates progress:** stages arrive when the server genuinely finishes them, and every duration printed is the real measured server time. What the client adds is a floor on how fast rows *appear* (`MIN_DWELL_MS = 420`), and the verdict is held until the last stage has been shown. For a video the pacing does nothing at all — the queue is empty while ffmpeg works, and you are watching the real thing. Measured: **reading takes 1067ms for `ceo_announcement.mp4` versus 3ms for a JPEG**, from the same code path.
- **Deviations (+why):** `plain_reason_strings` is a filtered, re-ordered view, not a 1:1 translation of `reasons`. `C2PA_MISSING` was leading every single plain card with "it had no built-in content credentials" — an absence of an optional feature, true of essentially every forwarded file, and pure noise to a lay reader; it and `NO_OFFICIAL_CLAIM` (which the plain body already states) are suppressed from the plain list only. The plain list also has its own ordering, deliberately *not* `_TOP_REASON_PRIORITY`: that ranks by alarm to pick LIKELY_FAKE's `{top_reason}`, whereas the plain list must put a caveat the reader has to act on (a revoked key) above the match that proved authenticity. `reasons` and `reason_strings` stay complete and unordered-as-before for the technical view and any downstream consumer.
- **Also fixed:** `scripts/smoke.py` now ends with a loud warning that it has replaced the demo world with its own fixtures. It silently wiping the registry has now cost debugging time in three separate sessions — a `/verify` against an empty registry honestly returns "no match", which reads exactly like a broken matcher.
- **How it was verified:** live against the running stack. SSE streams confirmed end to end for image and video, both locales (Hindi: stage labels, plain verdict, and the evidence lines "फ़ाइल बदल गई थी / जो दिखता है वह वही है"). All five verdict types produce correct plain copy and correctly-ordered plain reason lists. CORS *and* preflight confirmed on the new streaming endpoint specifically, since a CORS failure there would break the whole feature silently in a browser while curl kept working. Landing page and all 6 routes serve 200 with the new sections present. Regression: `pytest` 80/80, `smoke.py` PASS, `pnpm test` 831/831, `pnpm build` clean across 10 routes, `scripts/evaluate.py` still precision 1.000 / recall 1.000.
- **Not verified:** still no headless browser in this environment, so the live-check animation, the disclosure interactions and the landing page layout are confirmed by build, type-check and served HTML — not by watching them. The pacing constant in particular (420ms) is a judgement call that wants a human eye.

## Post-Epic 10: match evidence panel (+ two render bugs)
- **Status:** complete; verified against the live API on macOS. Not a spec epic: requested directly ("show how processing the image to see if it's true or fake").
- **Why:** the registry stage is the most persuasive thing this system does and it was being communicated as the string `phash_dist_4`. A judge could read the verdict but not check the working.
- **What shipped:** `pipeline/evidence.py` (pure `build_match_evidence()`: the two byte hashes, the two perceptual fingerprints, exactly which bits differ, the thresholds the result was measured against, and per-frame distances for video); `api/artifacts.py` (`GET /api/artifacts/{sha256}/preview`, serving the *registered* side of the comparison: published/withdrawn communications only, images only, one 404 shape for missing/draft/non-image so the endpoint can't be used to probe for unpublished drafts); `hashing.differing_bit_indices()` + `hashing.video_frame_distances()`; `i18n` `evidence` block in en + hi; `components/MatchEvidence.tsx` (side-by-side images, both fingerprints as 8x8 grids with differing cells ringed, a 0..64 distance scale with the match/near bands drawn to proportion, video frame strip); `tests/test_evidence.py` (11 tests).
  - The fingerprint grid is not a visualisation *of* the hash. A phash64 is a flattened 8x8 grid of DCT-sign bits, so cell (row, col) is literally bit `row * 8 + col` of the hex the API returns. Same for the differing-cell highlights.
  - The submitted image is rendered from a browser-side object URL, never uploaded for storage: `/api/verify` still doesn't persist what a user forwards, and that property was worth keeping.
- **Two real bugs found and fixed in the same render path:**
  1. **`{revoked_date}` was never populated by any caller.** `RenderContext` declared the field, both i18n files interpolated it, and nothing set it, so every `VERIFIED_NOTICE` card hit `.format()`'s `KeyError`, fell back to the *raw template*, and printed literal `{entity}` / `{date}` / `{revoked_date}` braces at the user. That is DEMO.md step 8, the finale. It survived every gate because the checks asserted on verdict and reason codes, never on body copy. Fixed at both ends: `verify.py._revoked_key_date()` supplies the real date, and `.format_map()` over a defaulting dict now degrades a single missing placeholder to an em dash instead of destroying the whole sentence.
  2. `{date}` rendered as a raw ISO timestamp (`2026-08-01T13:19:11.453271+00:00`) mid-sentence on the card. Trimmed to the date.
- **Deviations (+why):** `match_registry` now records the closest candidate it saw even when nothing crossed a threshold, so a miss can say "closest registered item was 32 of 64 bits away" instead of a bare "no match". This touches Epic 4's gate-tested module, so it is deliberately **observability-only**: the new fields are `closest*`, never the `candidate` field `decide()` reads, a miss still returns `kind="none"`, and `TestEvidenceDoesNotAffectDecisions` asserts the verdict and reason list are byte-identical with and without evidence being built. Comparison across algorithms is by *normalized* distance so a pdq256 miss doesn't outrank a phash64 one purely on bit width. Evidence is stored in `verifications.signals` so a re-render keeps its panel; rows predating this change render without one rather than erroring.
- **How it was verified:** live against a real seeded world on port 8001. `image1.jpg` at JPEG q50 → `VERIFIED`, and the panel shows the argument in one screen: **SHA-256s completely different, perceptual fingerprints identical (0 of 64 bits)**. `screenshot_sim` (2.5% crop + PNG round-trip) → distance 10 with real differing-bit indices `[5,6,7,18,27,43,53,54,56,62]`, i.e. exactly at the match line. Unrelated noise image → `INFORMATIONAL` + `miss` with closest 32/64 ("well past the 10-bit match line"), correctly not accusatory. Preview endpoint 200/`image/jpeg`; unknown hash 404. Key revocation → `VERIFIED_NOTICE` with a real date in the body (bug 1 confirmed fixed). Hindi checked end to end on the new copy. Regression: `pytest` 80/80 (69 + 11 new), `scripts/smoke.py` PASS, `pnpm test` 831/831, `pnpm build` clean across all 10 routes, and **`scripts/evaluate.py` still precision 1.000 / recall 1.000 / worst-transform 1.00**, which is the empirical proof the `match_registry` change is behavior-neutral.
- **Not verified:** no pixel-rendered browser pass. Still no headless-browser tooling in this environment (same limitation as Epic 10), so the panel's layout is confirmed by type-check and build, not by looking at it. Worth an owner click-through before the demo.
- **Environment notes (macOS, moved back from the Windows machine):** `backend/.venv` was absent and `frontend/node_modules` was a Windows install (vitest failed with permission-denied, then `MODULE_NOT_FOUND` on native binaries) — both rebuilt. `colima start` reported `fatal: did not receive an event with the "running" status` at the ssh ControlMaster step but the VM and daemon came up fine a moment later; retrying `docker` was enough, no reset needed. **Postgres auth failed from the host while `docker exec psql` succeeded**: the compose volume predates the password rotation and `POSTGRES_PASSWORD` only applies on first init, so the stored password was stale; `docker exec` was misleading because the container's local socket is `trust`. Fixed non-destructively with `ALTER USER` rather than dropping the volume. Port 8000 is held by two **stale TrustRail uvicorn processes from Jul 11** running three-week-old code (`/healthz` → `db:false`); per the standing no-broad-kills rule they were left alone and this work used port 8001 — they need a PID-targeted stop before the next demo.
